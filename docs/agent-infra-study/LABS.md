# 八周研究路线与实验记录方法

[返回总目录](README.md)

本路线保留原学习计划的八周主题，用已经生成的 24 篇笔记作入口。所有实验当前均为 **NOT RUN**；它们是后续学习任务，不是本轮已经获得的结果。

## 1. 八周阅读与产出

| 周次 | 主题 | 对应笔记 | 本周验收产物 |
|---|---|---|---|
| 1 | Agent Loop / 生命周期 | 三项目 01；遇到流协议再查 04 | 同一任务的三条调用链、Turn/Step/Attempt 对照表 |
| 2 | Tool Registry / 调度 / 错误 | 三项目 03；重点读上游调度测试 | 声明、审批、执行、结果的责任表；一个工具失败实验 |
| 3 | Sandbox / Shell / 权限 | Codex 03、DSH 03，OpenCode 03 作边界对照 | 威胁模型与取消后资源清理记录，不以审批代替隔离 |
| 4 | Session / Context / Compaction | 三项目 02，结合 04 请求构造 | 原始记录、活动历史、模型实际请求三视图 |
| 5 | Persistence / Replay / Recovery | 三项目 07 | 带 flush/claim/ownership 的故障窗口矩阵 |
| 6 | Plugin / Service / Capability | 三项目 05 | 组件替换与卸载时序；一个配置变化实验 |
| 7 | Subagent / Goal / 调度 | 三项目 06 | 父子身份、结果交付与取消传播；DSH Goal 双状态机 |
| 8 | 可观察性 / 评估 / 总结 | 三项目 08 + COMPARISON | 一次失败复盘、可复现测量方案与下一轮证据缺口 |

这里的周次是组织顺序，不是掌握期限。一个专题若仍无法解释失败路径，应留下未决问题并补实验，不靠增加阅读篇数代替理解。

## 2. 准备固定源码，不污染现有工作区

在专用学习目录中分别取得官方仓库，检出 [source-lock.json](source-lock.json) 中的完整 SHA。已有工作区先检查未提交修改，不在原开发目录直接切换研究版本。

```bash
# 示例：在各自独立仓库内运行；先确认没有需要保留的未提交修改。
git status --short
git rev-parse HEAD
git checkout --detach <source-lock.json 中该项目的完整 commit>
git rev-parse HEAD
```

本套笔记未安装依赖或构建项目。真正运行前，按该固定提交的仓库说明核对语言版本、锁文件、包管理器、平台限制和测试入口；不要从主分支最新教程复制一条可能不适配的命令。

## 3. 三项目共用的最小任务

准备一个完全本地的测试项目：两个只读文件、一处可修复的小错误、一组确定性测试、一个只写临时标记的工具。先使用 mock provider 固定输出顺序，再视需要增加真实模型对照。

共用任务是“读取文件、执行一个受控工具、收集结果、给出回答”。比较逻辑行为，不要求三个项目工具名称相同。模型、工具集合、权限、环境或超时不同，必须记录为实验变量。

第一轮不需要 GPU、不需要多节点 Kubernetes，也不需要真实客户资料。它的目标是验证执行语义，不是刷排行榜。

## 5. 实验记录模板

```text
实验 ID：例如 D03-A
状态：NOT RUN / PASS / FAIL / SKIPPED / INCONCLUSIVE
研究问题：
预期与依据：代码文件、符号、固定 SHA；或明确写“待检验假设”
环境：OS、架构、运行时、包管理器、是否容器/VM
版本：仓库 HEAD、依赖锁文件、profile/关键配置
模型：mock 或 provider/model；采样参数与工具集合
权限：审批、文件/网络/进程约束、临时工作区范围
命令：实际执行的原始命令
注入点：哪个 await/提交边界/工具调用前后
观测：输入接纳、模型请求、工具开始/结束、结果提交、flush/终态
实际结果：只写观察到的事实
解释：与预期一致吗？还有哪些替代解释？
证据：脱敏日志片段、断言、时间戳、文件散列
缺口：未观测的阶段、平台限制、跳过原因
复现：最小步骤与清理方法
```

不要把 PASS 定义为“Agent 最终说完成”。协议测试要看实际断言，业务任务要看外部验收。一次偶然成功也不能证明没有竞态。

## 6. 每个专题的四项验收

**执行图。** 能独立画出核心时序或状态机，并区分模型、运行时、存储和环境。

**源码定位。** 每个关键节点有固定提交的文件与符号，不只引用 README 概括。

**设计取舍。** 能解释为什么在这里使用快照、事件、状态机、注册表或队列，同时明确分析与作者决策记录的区别。

**失败验证。** 至少实际运行一个超时、取消、拒绝、溢出、配置变化或恢复场景，并记录未决边界。

## 7. 安全与数据纪律

使用临时目录、mock 工具和合成凭证。不要为测试方便把真实工作目录开放为 danger-full-access，不将公网监听或关闭所有审批作为默认设置。需要 OS 沙箱或进程中断实验时，在隔离 VM/容器和明确测试副本中运行。

不要制造真实系统磁盘耗尽，不删除个人会话数据库，不对生产服务 kill 或注入故障。遥测实验先使用本地 fake sink，未经明确选择不向真实端点发送日志。

公开笔记只保存最小脱敏证据。Prompt、工具结果、终端输出、代码路径都可能包含敏感内容，不能因为文件名叫 trace 就默认可公开。

## 8. 从学习转为工程能力

第一阶段完成后，优先贡献一个可复现 bug、一条缺失的确定性测试或一份有源码依据的文档修正。开源贡献是否被接受取决于项目维护者，不应以提交次数衡量质量。

之后再选择一个可量化问题向 Infra 延伸，例如减少环境冷启动、限制多任务输出内存、恢复中断的评测批次或隔离慢观察者。扩展前先写清继承了哪些单任务语义、哪些需要新的分布式协议。
