## 1. 本篇要解决的问题

一个用户请求可能引起多次模型采样、多个工具调用，以及执行过程中的新输入。真正的 Loop 不是简单地“没有 final answer 就再调用一次模型”，而是协调输入接纳、每次请求使用的配置、工具结果、取消和收尾。学习时要先区分 **Thread/Session 的长期状态、Turn 的一次工作生命周期、Step 的一次采样快照**，不要把它们都叫一轮。

## 3. 主执行路径：先看边界，再看细节

以下是阅读用的概念调用链，省略了部分钩子与分支，不是原函数逐行抄录：

```text
run_turn
  → 准备/复用本 Turn 的 ModelClientSession
  → 尝试前置 compaction，处理输入钩子与输入记录
  → 捕获 StepContext
  → 从当前历史构造模型输入
  → run_sampling_request
      → 流式模型事件
      → 工具执行及结果回收
  → 检查模型是否还需要工具后续请求、是否还有待处理输入
  → 必要时压缩并继续；否则进入停止/完成路径
```

**请求快照是一条贯穿链路的约束。** `run_turn` 不应让某个模型请求看见 A 版本工具，而在响应到达时按不相关的 B 版本配置执行；`ToolCallRuntime` 因此保留产生该工具调用的 `Arc<StepContext>`。[S1][S2]

**输入到达不等于输入已成为模型历史。** 前置压缩失败时，代码仍有处理钩子和记录输入的分支，随后才发布错误，避免错误发布导致新输入被导向一个只记录了一半的上下文。恢复代码中的 `RecordedTurnInput` 也只证明输入进入了记录路径，不证明已经落盘。[S1][S3]

**继续条件不是只看模型文本。** 已读分支把模型要求继续与 pending input 一并考虑。自动压缩还会影响下一次是否立即消费待处理输入。应该将“工具债务已偿还”“输入队列已处理”“停止钩子完成”分别画成状态条件，而不是用一个 `finished` 布尔值代替。[S1]

## 4. 学习重点与设计分析

### 快照所有权

学习 `TurnContext` 与 `StepContext` 的作用域。重点不是背字段，而是沿着字段找读写方：谁能更新下一 Step 的设置，谁只能使用已捕获的快照，异步工具是否还持有旧快照。**分析：** 这与配置版本化、请求级一致性属于同一种系统设计问题；它减少时间检查与实际使用之间的错位，但不是一个分布式配置一致性协议。

### 可取消工作与必须完成的结算

取消信号进入模型请求和工具执行；但“取消已发出”与“所有工具已停止、结果已记录”不同。工具层会对已经达到终态、需要完成取消清理的任务进行不同处理。[S2] 学习时要在时序图上标出 cancel request、handler stop、result settlement 三个时刻。

### 逻辑继续与传输重试

同一个 Turn 可以有多次 Step；同一 Step 的网络失败又可能带来重试。不能把请求次数当作 Turn 数，也不能把一次 HTTP 重发解释为再次执行工具。相关的传输状态见 [04](04-llm-streaming.md)。

## 5. 故障推演与待运行实验

**实验 C01-A：工具执行期间追加输入。** 使用 mock 模型先输出一个受闸门控制的工具调用；在工具尚未完成时发送一条新输入；释放工具后检查下一次模型请求。记录新输入被接纳的时刻、对应 Step 和工具结果在历史中的位置。验收不是“最终答对”，而是能解释它为什么进入该请求。

**实验 C01-B：前置压缩失败。** 在隔离测试中令压缩返回错误，检查原用户输入是否记录、错误通知在何时出现、重试是否重复接纳输入。此实验用于核对代码分支，本文没有执行结果。

**实验 C01-C：取消与后继输入竞争。** 在模型流和工具执行两个时间点分别取消，然后立即发送新输入。观察是继续现有 Turn 还是形成后续工作；不要预先假定所有取消路径一致。

## 6. 自测与验收

应能回答：为什么 ToolCallRuntime 要保留 StepContext？为什么 pending input 会影响停止条件？RecordedTurnInput 与 flush 分别证明什么？

最终产物是一张带三个 Step 的执行时序表：每次列出输入快照、模型请求、工具结果、取消状态和停止原因。每条边都能回到 [S1] 或 [S2]，未追到的路径明确标为待验证。

**迁移到 Agent Infra：** 请求版本化、执行状态机、接纳与完成分离可以迁移；本地 Loop 本身不证明多节点调度、租约或故障接管能力。
