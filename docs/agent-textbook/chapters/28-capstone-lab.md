# 第 28 章　综合实验：构建一个可解释、可中断恢复的教学 Agent

[教材目录](../README.md)

**先修知识：** 第 4、6、11、14、15、17、24 章，以及 Python 函数、异常和数据库事务的基本知识。**学习目标：** 把模型决策、工具授权、状态持久化与完成验证连成可运行闭环；通过失败注入解释恢复语义；区分流程机制测试、任务结果评测与模型能力评测；为自己的 Agent 写出可检验的完成条件。

## 28.1 为什么最后一个实验先不连接大模型

前面章节读过真实项目的大量执行路径，现在需要自己掌握这些路径的因果关系。如果第一次综合实验就连接真实模型，一次失败可能来自提示词、随机输出、凭证、网络、限流或执行器，很难知道自己学到了什么。本章先把决策来源固定下来，再验证执行器有没有兑现自己的承诺。

配套 [实验目录](../labs/README.md) 包含 [agent_lab.py](../labs/agent_lab.py)、[test_agent_lab.py](../labs/test_agent_lab.py) 和 [实际验证记录](../labs/verification.json)。程序仅使用 Python 标准库，不需要 API key 或网络。`ScriptedModel` 已经知道四步修复计划；它是可控的模型替身，**不能证明真实 LLM 会理解问题、发现算法或写出补丁**。本章所有“通过”都限定于教学程序和明确列出的测试。

任务仍是贯穿全书的 CSV 总价错误：

```csv
price,quantity
3.50,2
12.00,3
```

错误模式 `unit_only` 计算 `3.50 + 12.00 = 15.50`，正确模式 `quantity` 计算 `3.50 × 2 + 12.00 × 3 = 43.00`。金额用 `Decimal`。工作区是一条 SQLite 记录，“修改程序”只允许切换这两个预定义模式，不执行任意代码，不启动 shell，不修改真实项目。这项简化让我们能够把副作用、结果和日志放进同一事务，清楚观察什么已提交、什么仍未确定。

## 28.2 从数据契约到一次完整循环

先阅读 `ToolCall`、`TOOLS` 和 `validate_call()`。一次逻辑调用由稳定的 `call_id`、工具名称和参数组成。`inspect` 返回样本、模式和修订号；`test_total` 返回实际值、期望值、是否通过及被测修订号；`set_mode` 只接收枚举参数 `mode`。验证器拒绝未知工具、多余字段、缺失字段和无效枚举。这里实现的是本实验需要的 schema 子集，不是完整 JSON Schema 引擎。

`ScriptedModel.next_call(context)` 从四步计划中选择第一个尚无持久结果的调用：

```text
inspect → test-before → repair → test-after → 请求结束
```

`test-before` 返回 `passed=false` 是一份成功取得的诊断结果，不是工具基础设施故障；Agent 应据此进入修复步骤。相反，注入的 `TransientFailure` 表示本次工具没有产生结果，需要重试。这个区别直接决定是否推进计划。

运行器的教学伪代码如下；实际实现还包含各边界的事件记录：

```text
循环：
  持久预留一次模型决策预算
  构造并压缩上下文
  取得模型的下一步
  若模型要求结束：检查完成条件，记录终态
  否则：校验调用；复用已完成收据；检查审批
        持久预留一次工具尝试预算
        在事务中执行工具、保存结果与副作用收据
        暂态失败则保留 pending，并有界重试
```

工具执行器与模型之间的边界至关重要：模型提出 `set_mode`，但只有 `execute()` 检查过授权后才能修改。模型看到的约束文本有助于决策，却不能取代执行器的审批判断。

## 28.3 用状态与不变量定义“完成”

数据库使用五张小表：`run` 保存状态与两种预算；`workspace` 保存数据、模式和修订；`calls` 保存逻辑调用及完成结果；`effects` 保存修改收据；`events` 保存带序号的事件。调用首次登记与最终完成可以相隔多次重试，所以结果另有 `completed_seq`，按**完成顺序**读取。用首次登记顺序寻找“最新测试”，会让早期失败、后来才成功的新验证被较早完成的旧验证遮蔽。

成功不是“模型说结束”，也不是“数值现在看起来正确”。本实验同时要求：

1. 没有已接纳但尚未结算的调用，即 `pending` 为空。
2. 最近完成的 `test_total` 通过，且对应当前工作区修订。
3. 当前程序模式通过五项固定验证；其期望值是手工计算的金额，覆盖数量大于一、零数量、空数据、小数金额和数量为一。

第三项避免一个容易忽略的假成功：如果当前用户样本的 quantity 全为一，错误模式与正确模式输出相同。仅测试该样本会错把“没有暴露错误”当作“错误已修复”。固定验证集扩大了检查范围，但仍不能证明任意 CSV 都正确；非法字段、货币舍入规则和巨大输入等问题没有在本实验中全面评估。

预算也需要两个单位。`spent` 计实际启动的工具尝试；`decisions` 计 `run()` 中模型决策次数。缓存回放不启动工具，因此不增加 `spent`；但模型不停索取同一缓存结果仍会消耗 `decisions`，不能永远循环。两个计数都在对应动作开始前提交，恢复不能退还已经预留的预算。直接调用 `execute()` 没有调用模型，因此不消耗决策预算。

`--approve-edit` 只批准 `set_mode(mode="quantity")`。未批准时程序持久保存等待状态和请求事件，然后暂停；批准本身由本次运行参数提供，没有被保存为永久授权。`pending` 专指已接纳并启动、尚无结果的调用，不包含尚未通过审批的请求。

## 28.4 先运行，再解释每个输出

从仓库根目录运行：

```sh
python3 docs/agent-textbook/labs/agent_lab.py demo --approve-edit --events
python3 -m unittest discover -s docs/agent-textbook/labs -p 'test_*.py' -v
python3 docs/agent-textbook/labs/agent_lab.py evaluate
```

正常演示的实际汇总为：

```json
{"status":"completed","spent":4,"max_attempts":8,
 "decisions":5,"max_decisions":16,"mode":"quantity",
 "revision":1,"total":"43.00","effects":1}
```

四次尝试对应四次工具执行，第五次决策请求结束。事件中应能找到修订 0 的失败测试和修订 1 的成功测试，最终 `finished` 事件包含 `oracle_passed=5`、`oracle_cases=5`、`pending=[]`。日志不是装饰：如果只看到 `tool_started`，不能据此声称已经修改；如果只有修复收据，没有当前修订的测试，也不能声称完成。

本次在 2026-10-13、Darwin arm64、Python 3.12.8、SQLite 3.45.3 上实际运行了 **23 项测试，全部通过**。测试包含子进程真实退出后的恢复。五个固定数据夹具中，错误程序碰巧通过 **2/5**，脚本化流程通过 **5/5**。分母是五个已知数据夹具，没有调用真实模型，没有运行三个上游项目的测试，也没有测量它们的性能或能力。

可以立即做两个对照：省略 `--approve-edit`，得到 `waiting_approval / spent=2 / effects=0`；设置 `--approve-edit --max-attempts 3`，虽然结果已经变成 `43.00`，仍得到 `budget_exhausted`，因为修改后的工具验证尚未完成。这两个结果分别证明“能提出动作”与“获准执行”、“修改正确”与“任务已验证”不能合并。

## 28.5 通过崩溃位置推导恢复结果

在新目录保存数据库：

```sh
lab_dir=$(mktemp -d)
python3 docs/agent-textbook/labs/agent_lab.py demo --db "$lab_dir/before.sqlite3" --approve-edit --crash-before repair
python3 docs/agent-textbook/labs/agent_lab.py demo --db "$lab_dir/before.sqlite3" --approve-edit --events
```

第一条命令预期以代码 86 退出，它在修改事务提交前执行 `os._exit`。恢复打开数据库时，工作区仍为 `unit_only`，修改收据和结果均不存在；但第三次工具尝试已经在较早的事务中扣除。重新修改和验证后，最终为 `spent=5 / effects=1`。

将数据库换为新文件，并把故障参数改成 `--crash-after repair`，再恢复：退出发生在事务提交后、调用方收到返回值前。修改、收据和结果一起存在，脚本模型读取这些结果，直接继续剩余测试；最终为 `spent=4 / effects=1`。单元测试还主动重放同一个 `call_id`，确认执行器返回原收据，不再次修改。相同 ID 携带不同工具或参数则触发冲突；更换 ID 会被视为新动作，不能得到语义去重保护。

| 故障窗口 | 恢复时已有事实 | 本实验的动作 |
| --- | --- | --- |
| 预留预算后、工具效果提交前 | 尝试已计费，调用 pending，无已提交修改 | 在剩余预算内重试 |
| 修改、结果与收据已提交，返回前 | 相同调用的结果与副作用均可查询 | 复用收据或继续下一步 |
| 验证通过后又产生新修订 | 旧验证只证明旧状态 | 禁止用旧验证完成 |
| 已有通过验证，但仍有 pending 调用 | 执行责任尚未结算 | 禁止完成 |

关键限制必须与成果一起记住：原子性仅覆盖这一个 SQLite 数据库。若工具真的修改外部文件或调用远程 API，外部副作用与本地收据不再天然同事务，仍需幂等键、后置条件查询、协调协议或人工处理不确定结果。本实验没有证明通用 exactly-once，也没有测试断电、磁盘损坏或多个 worker 并发写入。

## 28.6 压缩上下文，并映射回真实项目

`compact_context()` 将最近事件裁成尾部，同时逐字保留结构化的目标、约束、pending、预算状态和工具结果。这样可以亲手验证一个小而明确的不变量：裁剪日志不会删除审批要求或把未完成调用藏起来。完整事件仍在数据库里；压缩后的模型上下文不是持久化存储的替代品。

它没有实现语义摘要，也没有对任意数量的工具结果提供 token 上限。`build_context()` 仍会读取全部实验日志，固定计划只有四个工具结果。若要处理数天任务，需要选择证据、摘要质量检测、检索与按需加载；不能把本实验尾部截取函数直接称为生产级上下文管理。

本章代码是教学抽象，不是任何一个项目的微型复刻。对照应沿前文已核查的路径继续阅读，而不是按类名认定实现相同：

## 28.7 练习、参考答案与开放实验

1. **状态题：** 为什么 `total=43.00` 仍可能是失败或暂停？<br>
   **参考答案：** 可能未验证当前修订、存在 pending、固定 oracle 未通过，或预算在终态判断前耗尽。数值只是一个观测，任务完成是多个约束的合取。

2. **故障题：** 提交前崩溃后，为什么副作用只有一次，尝试数却增加？<br>
   **参考答案：** 预算预留与效果事务分开。前者已经提交，后者回滚；重试属于新的尝试。保守记账防止通过不断崩溃无限获取免费工具执行，但可能把未产生效果的启动也计入预算。

3. **追踪题：** 测试 A 先登记后失败；测试 B 验证修订 1；修改得到修订 2；A 重试后验证修订 2。应以哪个结果判断完成？<br>
   **参考答案：** 以最后完成且匹配当前修订的 A 为依据。首次登记顺序不代表观察新旧，因此本实验保存 `completed_seq`。仍须检查 pending 和固定 oracle。

4. **设计题：** 把 `set_mode` 改成远程发单工具，能否照搬同一 SQLite 事务避免重复订单？<br>
   **参考答案：** 不能。远程提交与本地收据之间存在不确定窗口。应先明确远端是否接受稳定幂等键、能否查询订单后置条件以及冲突处理方式；无法确定时应停在未知状态，而不是自动换 ID 重试。

5. **实验题：** 编写一直返回同一 `inspect` 的模型，预测工具尝试数和决策数；关闭程序后提高构造参数再恢复会怎样？<br>
   **参考答案：** 首次调用产生一次工具尝试，后续返回缓存；决策数达到原持久上限后停止。新的构造参数不能修改已有预算。对应回归测试为 `test_cached_replay_consumes_persistent_decision_budget`。

可继续做三项**尚未运行的开放实验**：将压缩改成摘要并建立约束丢失检测；引入假远程服务模拟“远端成功、本地未记录”，比较幂等键和后置条件查询；替换脚本模型为真实模型，使用留出的任务、相同预算和多次运行测量完成率及成本。接入真实模型之前，应先保留现有测试作为运行器回归基线，不能把换模型后的单次成功当作新增机制已被证明。

综合作业可按以下标准评分：任务与授权契约 20%、状态与恢复不变量 25%、失败注入及独立验证 25%、解释日志和成本 15%、局限与可复现说明 15%。若仍能在 pending 未结算时宣称完成，或把未知外部副作用自动重试为新调用，应先修正完成语义，再讨论模型效果。
